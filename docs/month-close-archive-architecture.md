# 月度归档并确认发薪：统一架构与操作规范

## 一、产品定位

**月报页是唯一的正式月度归档入口。** 用户在月报点击“月度归档并确认发薪”后，系统同时固化本月最终排班依据与冻结薪资快照。排班表仅保留排班编辑、薪资生成、班次设置和“清空本月”纠错功能；不再提供手动存档、历史版本、锁定/解锁或一键代入入口。

| 月份状态 | 月报主操作 | 数据写入规则 |
|---|---|---|
| `DRAFT` | 月度归档并确认发薪；无薪资时显示“归档本月（无发薪）” | 创建当前月 `MonthCloseArchive` v1。 |
| `FROZEN` | 查看月度归档；进入差额调整 | 正式排班和薪资不可直接修改。 |
| `ADJUSTING` | 放弃调整；重新归档并确认 | 修改基于隔离会话，重新确认创建 v2。 |

## 二、归档内容

一个 `MonthCloseArchive` 包含完整且不可变的结算依据。

| 数据 | 维度 | 用途 |
|---|---|---|
| `scheduleByDept` | 部门 | 固化最终排班记录、员工数和班次数。 |
| `payrollByEmployee` | 员工 | 固化应发、实发、考勤工资、补贴、绩效、提点、扣款、预支等薪资字段。 |
| `summary` | 月份 | 固化员工数、应发、实发和扣款汇总。 |
| `adjustments` | 员工差额 | 对比前一正式归档版本，记录本次重新归档的增减金额与明细。 |

创建 v2 时，v1 会标记为 `superseded`，但仍可在月报归档详情中只读查看。系统不会覆盖或删除正式历史版本。

## 三、冻结月差额调整

进入差额调整必须填写原因。系统创建 `MonthAdjustmentSession`，其中保留开始调整瞬间的本月排班、考勤与薪资基线。

```text
FROZEN v1
  → 填写调整原因
  → ADJUSTING（建立可回滚基线）
  → 修改排班 / 考勤 / 薪资草稿
  → 重新归档并确认
  → FROZEN v2
```

放弃调整会使用会话基线完整恢复排班、考勤与薪资，然后删除该会话。冻结 v1 不会被修改。

在 `ADJUSTING` 状态，月报的归档详情可以“应用此归档排班到调整草稿”。这承接旧历史版本的一键代入能力，但只允许在调整会话内操作，且会触发当月考勤薪资重新计算。

## 四、旧数据清除策略

本次重构**不迁移旧数据**。应用加载新的归档 Store 后会永久删除：

```text
labor_schedule_snapshots_v1
labor_payroll_confirmations_v1
PaySlip 中的 frozenAt / frozenBy / frozenSnapshot
```

因此，旧手动排班快照和旧确认发薪记录不会出现在新归档中心，也不会与新状态机混用。

## 五、权限与写入守卫

所有排班、考勤、绩效、补贴、预支和薪资写入均通过 `isMonthWritable(month)` 控制。

| 状态 | 自动同步 | 常规编辑 | 归档排班恢复 |
|---|---:|---:|---:|
| `DRAFT` | 允许 | 允许 | 无正式归档可恢复 |
| `FROZEN` | 禁止 | 禁止 | 禁止 |
| `ADJUSTING` | 允许 | 允许 | 允许，仅写入调整草稿 |

归档创建和调整会话创建均等待员工、排班、考勤和薪资数据加载完成，防止异步加载过程产生空归档。

## 六、发布前验证

发布前至少执行：

```bash
pnpm check
pnpm test
pnpm test:h5:schedule-correction
```

H5 自动化验证覆盖 375pt、390pt、430pt 排班表布局，以及 375pt 月报 `DRAFT`、`FROZEN`、`ADJUSTING` 三态的归档交互和根级横向溢出保护。
