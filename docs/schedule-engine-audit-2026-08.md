**审计结论：** 本次已修复会直接导致**节假日薪资错误、调休重复扣减、跨月绕过锁定、快照误删其它部门排班、配置加载覆盖**的确认问题；同时完成了真实生产考勤引擎的单元化和 38 项专项回归测试。完整测试集现为 **41 个测试文件、922 项测试、0 skipped、全部通过**。

> 本报告中的法规内容仅用于产品规则核对与工程风险识别，并不构成个案劳动、薪酬或税务意见。实际规则须以员工合同、所在地、适用工时制度审批与专业意见为准。

## 一、审计方法与全链路边界

审计没有只检查页面显示，而是沿着“**班次写入 → 月度考勤 → 薪资草稿 → 发薪锁定/导出**”逐段复核数据所有者、日期过滤、持久化键、异步加载、重试幂等性和用户可触达入口。审计代码覆盖了 `app/labor.tsx`、`lib/labor/store.tsx`、`lib/labor/types.ts`、`lib/labor/import.ts`、`lib/labor/validation.ts`、`lib/labor/export.ts`、`app/labor-attendance.tsx`、`app/period-analysis.tsx` 与相关测试。

成熟餐饮排班产品通常将可用性、岗位/技能、覆盖人数、发布版本、换班审批、加班、休息间隔和数字审计轨迹作为同一排班域内的预防性控制。7shifts 将需求预测、技能平衡、加班预警和关店后次日开店（clopen）预警放入建表阶段；其培训示例把连续班间 **少于 11 小时休息**作为风险阈值。[3] [4] Deputy 同样在排班前提示加班、休息、缺少休息和薪酬规则，而不是等薪资生成后才暴露问题。[5]

| 链路层级 | 主数据/当前实现 | 本次审计关注点 |
|---|---|---|
| 排班计划 | `labor_shifts_v1` 的 `ShiftEntry` | 日期、员工、班次、特殊状态、跨月单元格、批量写入与删除 |
| 规则配置 | 班次模板、特殊状态、节假日、灵活工时 | 配置是否真的进入计算、模板变化是否留下幽灵记录 |
| 考勤派生 | `MonthlyAttendance` | 工时、出勤日、加班、节假日补偿、比例底薪、月份隔离 |
| 调休余额 | `CompOffBalanceEntry` | 存入、扣减、兑现、节假日来源、重试幂等、历史迁移 |
| 薪资派生 | `PaySlip` | 节假日拿钱/换休、控制字段保留、自动同步、年度累计税额 |
| 月度治理 | 确认发薪状态机、排班快照 | 冻结、调整期、跨月权限、快照恢复部门范围 |
| 旁路模块 | `period-analysis` 独立配置 Store | 是否覆盖主排班或在加载前写入默认值 |

## 二、已确认并修复的问题

### 2.1 P0：节假日配置曾被传入却未被真实考勤引擎消费

`SchedulePage` 会构造 `holidayDaysList`，其中包含节假日日期、倍率以及已经按员工适用范围筛选的结果；但旧 `calcFromShifts` 从未读取该参数。因此普通班次落在已配置的节假日日期时，不会产生倍率补偿，`HolidayConfig.multiplier` 与 `applicableEmployeeIds` 实际没有进入薪资结果。

现已将生产逻辑提取到 `lib/labor/attendance-calculator.ts`，由 Store 唯一委托调用。计算器会将配置化节假日倍率应用于正常工作班次；当节假日特殊状态和节假日配置同时存在时，配置倍率优先，而历史 `ss_holiday` 的 key 保持兼容。该规则与“配置化薪酬规则应在排班生成阶段实际生效”的行业实践一致。[3] [5]

| 修复项 | 修复前 | 修复后 | 防回归测试 |
|---|---|---|---|
| 普通班次节假日倍率 | `holidayDaysList` 未使用 | 按日期映射参与 `holidayBonus` | Suite A2、A4、A5、B1、B2 |
| 员工适用范围 | 配置筛选结果未进入工资 | `getHolidayForDate` 筛选后的规则进入真实计算器 | Suite A2 |
| 特殊状态与配置冲突 | 无明确优先级 | 节假日配置倍率优先，历史状态 key 保持不变 | Suite A3、I3、I4 |
| 生产/测试漂移 | 测试镜像存在正确逻辑，生产 Store 未实现 | 测试改为直接调用真实纯计算器 | Suite A–B、G–H |

### 2.2 P0：节假日“拿钱/换休”对话框无入口，且自动同步会把换休补偿加回工资

旧代码中存在 `runPayrollGeneration` 和节假日决策 Modal，但仓库内没有 `setShowHolidayDecisionModal(true)` 调用，导致决策流不可达。即使旧数据中存在“换休”选择，后续自动同步也从基础排班重算考勤，重新把节假日补偿加入工资。

现已在排班控制栏加入紧凑的“生成薪资单”图标入口；入口扫描当月实际节假日工作记录，用户可以选择拿钱或换休。`holiday-pay.ts` 统一从 `PaySlip.holidayBonusAllocation` 读取换休部分，并在 autoSync 时从现金补偿和考勤工资中剔除，避免路由返回、改排班或状态同步后出现“换休又拿钱”的错误。

### 2.3 P0：调休余额存在双数据源、余额消费可重复发生

项目历史上同时保留 `HolidayCompOffEntry` 和 `CompOffBalanceEntry` 两套节假日调休余额。实际生成节假日换休时写入的是 `CompOffBalanceEntry(source="holiday")`，而部分消费和展示逻辑却读取旧 Store，导致余额来源、展示和扣减不一致。旧生成函数每次执行还可能再次从余额中扣除同一条调休排班。

现已统一业务读取、展示与消费至 `CompOffBalanceEntry`，以 `source="overtime" | "holiday"` 区分来源。保留旧 Provider 仅做一次性历史迁移：旧记录被迁入统一 Store 后以 `migratedToUnified` 标记，不再进入业务计算。薪资单新增 `compOffUsage` 审计字段，以“日期 | 班次 | 特殊状态”记录一次消费；重复生成会跳过已经消费的同一排班。手动“减少天数”也改为支持部分扣减并在余额不足时拒绝操作，避免提示成功却未实际扣减。

### 2.4 P0：跨月日历可依据当前视图月份绕过已锁定月份

月视图会展示相邻月日期，但旧单元格编辑、批量删除和快速填充仅检查 `currentMonth`。用户在未锁定的 7 月视图中可以操作实际属于已锁定 6 月的跨月单元格。

现已新增 `schedule-guards.ts`：任何写入前都从实际 `YYYY-MM-DD` 取月份，汇总所有非可写月份并给出明确提示。该守卫已接入单元格保存/清空、批量删除、两种快速填充与快照代入。该修复把“月度锁定”从页面状态提升为数据日期层的规则。

### 2.5 P0：快照恢复会删除当前月其它部门的排班

快照本身按部门存档，但恢复时旧代码将 `monthShifts` 全量转换为删除列表，随后仅写回当前部门的快照；因此恢复前厅快照会删除后厨同月排班。现已把删除范围过滤到 `allDeptEmployees`，并在恢复前检查当前月是否可写。

### 2.6 P1：独立时段分析排班 Store 可在异步加载前持久化默认值

`period-analysis` 仍有独立的营业时间与班次配置键，和主排班规则不共用；虽然它不直接写入 `labor_shifts_v1` 或薪资链路，但原 Store 在 AsyncStorage 尚未加载完成时即可写入默认值，慢设备上存在覆盖已有配置的竞态。现已加入 `hydrated` 守卫，并恢复重载监听清理回调。

## 三、移动端与交互验证

新增“生成薪资单”入口使用 32pt 紧凑图标按钮，不增加文本宽度；控制栏在 375pt 宽度下仍可容纳两个分段控件、编辑按钮和四个图标按钮。按钮设置了无障碍标签“生成薪资单”。此前已完成的金额卡片字体自适应保护继续适用，排班本次新增逻辑没有引入横向 ScrollView 或更宽的单元格内容。

跨月单元格仍以淡色显示，但现已从“视觉提示”升级为“写入层校验”。即使用户通过长按快速填充、清空或历史代入等非普通点击路径进入写操作，也会按目标日期所属月份检查锁定状态。

## 五、与专业排班产品和法规基准的对照

中国劳动法规定了工作时间、每周休息、延长工时和加班工资的基本边界；2025 年人社部明确月制度工作日为 **20.67 天**、月计薪天数为 **21.75 天**，并明确日/小时工资折算不剔除法定节假日。[1] [2] 当前产品已具备排班到月度薪资的基础链路，但仍应将以下行业能力作为下一阶段建设目标。

| 专业能力 | 当前状态 | 风险或影响 | 建议优先级 |
|---|---|---|---|
| 发布/变更审计轨迹 | 月度发薪锁定和快照存在；排班单条修改无操作者、理由、版本轨迹 | 发生工资争议时难以解释谁在何时改了哪一班 | P1 |
| 员工可用性、请假与换班审批 | 未见统一 Availability/Leave/Swap 域 | 易出现个人冲突、无授权换班与缺员 | P1 |
| 岗位资格、最低覆盖人数、经验搭配 | ShiftTemplate 仅有名称、时间、默认工时 | 无法提前识别吧台/前厅/后厨技能缺口 | P1 |
| 班间休息、日/周/月工时预警 | 只计算月度汇总加班，没有连续班间隔、日/周阈值规则 | 可能产生疲劳、超时与用工风险 | P1 |
| 计划班次与实际打卡分离 | 当前排班工时直接驱动考勤和工资 | 计划变更或未出勤时无法形成实际工时证据链 | P1 |
| 统一模板身份 | ShiftEntry 只保存班次 `session` 文本，不保存 templateId | 模板改名或删除后，历史排班仍被计薪但可能不在网格中显示 | P1 |
| 法定工资基数策略 | 内部 `dailyRate = baseSalary / (当月天数 - 休息天数)` | 与 21.75 日计薪天数的法定折算用途不同；特殊状态/节假日补偿应有可配置政策与审核 | P1 |
| 独立 period-analysis 规则 Store | 已修复提前持久化；仍是独立配置域 | 主排班和时段分析显示的营业时间/模板可不一致 | P2 |
| 本月调休排班删除后的余额回滚 | 生成重试已幂等；删除已经消费的调休排班时未自动逆向恢复余额 | 需要在“差额调整”中设计可审计的逆向分录，不能静默恢复 | P1 |

> 7shifts 的实务建议是将可用性集中管理，至少提前两周发布排班，并在建表时预警加班、休息不足与不合规班次；其示例特别强调避免关店后次日开店的连续班。[3] Deputy 强调用电子记录保留排班、工时、休息与变更，用于工资计算和审计。[5]

## 六、建议的后续实施顺序

第一阶段应将 `ShiftEntry` 从仅有 `shift: string` 演进为持久化 `templateId` 与显示名称快照，同时提供模板改名迁移和删除前影响预览。这样可消除“班次改名后历史班次幽灵化”的核心风险。

第二阶段应建立独立的“计划班次、实际打卡、请假/可用性、换班审批”四层模型。薪资应优先消费已确认的实际工时，而不是直接把计划表当作事实工时；每个换班和调休逆向操作都应产生不可变审计事件。

第三阶段应新增可配置的规则引擎：最短班间休息、日/周/月工时、法定节假日、未成年/特殊员工限制、岗位资格与最低人数覆盖。界面应在排班写入前给出明确的阻断或预警，而不是只在月末结算时发现异常。[3] [5]
