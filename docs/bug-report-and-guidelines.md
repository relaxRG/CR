# 薪资引擎时序 Bug 根因分析与开发规范建议

本文档针对近期在 `saveRewards` 逻辑中发现并修复的薪资重算时序 Bug 进行深入分析，并提出系统性的开发规范建议，以避免类似问题再次发生。

---

## 一、 Bug 根因深度剖析

### 1. 现象描述
在员工薪资卡片中编辑保存“临时奖惩明细”时，系统成功更新了奖惩明细条目，但界面上显示的“税前工资（grossSalary）”和“实发薪资”却**未包含新录入的奖惩金额**。

### 2. 根因分析
该 Bug 的本质是一个**时序竞争与状态读取滞后**问题。

在修复前，`saveRewards` 的代码逻辑如下：
1. 首先调用全量重算引擎 `buildPaySlipDraft`，期望获取包含新奖惩金额的薪资单草稿。
2. 随后调用 `upsertPaySlip`，将草稿与新的 `rewardPenalty`（奖惩总额）合并写入 Store。

**致命漏洞在于**：`buildPaySlipDraft` 是一个纯函数，它内部需要读取当前的 `existing` 薪资单状态（通过 `ref.current.find`）来计算 `grossSalary`。由于我们在调用它之前，**并没有将新的 `rewardPenalty` 写入 Store**，导致 `buildPaySlipDraft` 读取到的仍然是旧的奖惩总额。
因此，引擎基于旧值计算出了旧的 `grossSalary`，随后第二步的覆盖操作虽然更新了界面上的奖惩明细，但 `grossSalary` 已经被“锁定”为错误的值，导致最终的应发薪资不正确。

### 3. 修复方案：「先写 Store，再重算」
修复此 Bug 的关键在于理顺状态的依赖关系。我们采用了与 `writeToPaySlip` 相同的原子性单次写入模式：
1. **预写入（Patch）**：先调用 `upsertPaySlip({ ...slip, rewardPenalty: totalReward })`，将新的控制字段（奖惩总额）写入 Store。
2. **触发重算**：此时 `ref.current` 已更新。随后调用 `buildPaySlipDraft`，引擎便能正确读取到最新的奖惩总额，从而计算出正确的 `grossSalary`。
3. **最终覆盖**：将重算后的草稿覆盖回 Store，完成闭环。

该修复已在 commit `fd286b0` 中提交。

## 二、 关联逻辑与引擎扫描结论

为了确保该修复方案的彻底性，我们对项目中所有涉及薪资写入的逻辑进行了全量扫描。

### 1. 已正确使用该模式的逻辑
扫描确认，以下核心写入逻辑均已正确实现了「先写 Store，再重算」模式，不存在时序问题：
- **`writeToPaySlip`**（`labor-kpi-allowance.tsx`）：绩效补贴页的核心写入函数，完全遵循该模式。
- **`handleCashOut`**（`labor.tsx`）：调休余额兑现逻辑。
- **`toggleMode`**（`labor.tsx`）：节假日补偿分配逻辑。

### 2. 轻量增量更新逻辑（无需修改）
在 `labor.tsx` 中，存在三个专门处理预支与备用金关联的函数：
- `syncAdvanceToPaySlip`
- `syncLinkToPaySlip`
- `removeLinkFromPaySlip`

这三个函数采用了直接加减 `finalSalary` 的增量计算方式，而没有调用 `buildPaySlipDraft`。**经核实，这是有意为之的正确设计**。因为预支和备用金扣款发生在“税后”，仅影响 `advanceAmount`、`pettyLaborPaid` 和 `finalSalary`，不影响 `grossSalary` 及税费计算。采用增量计算避免了不必要的全量重算开销。同时，系统中的 `autoSync` 机制（500ms 防抖）会在底层依赖发生变化时自动覆盖这些增量更新，确保了最终一致性。

### 3. 废弃代码清理
在审查过程中，我们发现在 `labor-kpi-allowance.tsx` 的 `selectWorkKPITier` 和 `updateRevenueActual` 函数内部，残留了 `newWorkKPITotal` 和 `newRevenueKPITotal` 两个局部变量。这两个变量是旧版局部增量引擎迁移到全量重算模式时遗留下来的**死代码**（计算后从未被读取）。我们已在 commit `97d5c2c` 中将其彻底清理。

## 三、 开发规范建议

为了在未来的开发中彻底杜绝此类状态同步与计算滞后问题，我们提出以下开发规范：

| 规范维度 | 详细要求 |
| :--- | :--- |
| **状态依赖与时序** | **强制遵循「先写 Store，再重算」模式**。任何依赖于 Store 中现有状态的纯函数（如 `buildPaySlipDraft`），在被调用前，必须确保其依赖的底层控制字段（如奖惩、绩效选项、补贴开关）已经成功 `upsert` 到 Store 的 `ref.current` 中。绝不允许“先传参计算，再覆盖状态”。 |
| **全量重算 vs 增量更新** | 明确界定两种更新模式的适用边界。**税前因素**（如底薪、考勤、补贴、绩效、奖惩、调休兑现）的任何变动，**必须**调用 `buildPaySlipDraft` 进行全量重算，因为它们会引发社保、公积金、个税的连锁反应。**税后因素**（如已预支（advanceAmount + pettyLaborPaid））则允许使用轻量的增量计算（直接加减 `finalSalary`），但必须配合底层 `autoSync` 机制确保最终一致性。 |
| **死代码与旧逻辑清理** | 在进行重构或引擎升级（如从局部增量引擎升级为全量重算引擎）时，必须在同一 PR 中彻底清理所有未使用的局部变量、废弃的计算函数以及过时的注释。保持代码库的极简，避免给后续维护带来理解成本。 |
| **单向数据流与单一事实来源** | 薪资单草稿（PaySlip）应当是唯一的事实来源。所有前端 UI 组件（如绩效页、薪资卡片）在初始化和渲染时，必须直接从 Store 读取最新状态，严禁在组件内部维护与 Store 脱节的独立 State。 |

通过严格执行上述规范，我们可以确保 Cocktail R 的底层计算引擎在面对复杂的业务规则和高频的用户交互时，始终保持绝对的精确性和稳定性。

### 5. 表单与设置页的写入模式选择
- **强关联、重计算页面（如绩效补贴）**：必须采用「整页编辑，统一保存」模式。进入页面时加载状态到本地 `useState`，用户修改只更新本地 State，点击「保存」时一次性写入 Store 并触发全量重算。避免频繁触发重算带来的性能损耗，同时防止不完整的中间状态被写入 Store。
- **独立配置页面（如员工档案、制冰设置）**：如果各个字段之间没有强计算依赖，可以采用「整页保存」（如员工档案）或「即时写入」（如制冰设置，每个配置项独立修改），但必须保证每次写入都是原子操作。
