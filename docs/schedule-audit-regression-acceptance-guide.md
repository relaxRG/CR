# 排班审计回归测试验收指南

**适用对象：** 运维、QA、门店管理员、发布负责人  
**适用版本：** `0fdfb41` 及后续包含排班审计修复的构建  
**自动化基线：** `tests/schedule-engine-audit.test.ts`，共 38 项测试  
**最后更新：** 2026-08-11

> **验收原则：** 排班是考勤与考勤工资的唯一事实来源；已确认发薪月是历史结算事实，不能被自动同步静默重算。若无排班却仍存在金额，必须区分它是错误的“考勤底薪”，还是经规则或人工确认的补贴、绩效、提成、奖惩、调休兑现或已锁定历史薪资。

本指南覆盖排班、节假日倍率、调休、跨月锁定、快照恢复、月份隔离、兼职规则以及工资折算的回归验收。发布前必须同时满足以下准入门槛；任何一项失败，均不得将该构建作为薪资结算版本发布。

## 二、测试数据夹具与预期工资口径

为了让 QA 能够独立复算，建议建立以下隔离测试员工。示例使用 **2026-07**，该月有 31 天；员工月休 8 天，因此应出勤天数为 `31 − 8 = 23` 天。

| 字段 | 全职基准员工 F01 | 兼职基准员工 P01 | 用途 |
|---|---:|---:|---|
| 员工类型 | 全职 | 小时兼职 | 验证全职比例底薪与兼职小时工资分支 |
| 月底薪 | ¥6,000 | ¥0 | F01 比例底薪基数 |
| 月休天数 | 8 天 | 不适用 | F01 应出勤 23 天 |
| 加班时薪 | ¥50 | ¥50 | 验证加班与兼职小时计薪 |
| 常规班次 | 8 小时 | 8 小时 | 常规排班输入 |
| 节假日配置 | 7 月 1 日，倍率 3 | 同配置 | 验证全职倍率与兼职豁免 |

全职员工的当前内部比例底薪口径如下。它用于**考勤工资**，不是将任何月的工资机械固定除以 21.75 的法定折算口径。

```text
应出勤天数 = max(0, 当月自然日天数 − 员工月休天数)
出勤天数   = 当月有实际工时的排班日期数
            + 计入出勤的特殊状态日期数
            + 调休状态日期数

日薪原始基数 = 月底薪 ÷ 应出勤天数
比例底薪 =
  0，若应出勤天数 ≤ 0 或出勤天数 = 0；
  日薪原始基数 × 出勤天数，其他情况。

日薪原始基数保留完整精度；比例底薪、节假日补偿、特殊状态扣减和调休兑现都从这一基数计算，最终金额才保留两位小数。

考勤工资 = 比例底薪 + 加班费 − 特殊状态扣减 + 节假日现金补偿
```

例如，F01 在 2026-07 的应出勤天数为 23 天。日薪原始基数为 `¥6,000 ÷ 23`；若出勤 22 天，则比例底薪为 `(¥6,000 ÷ 23) × 22 = ¥5,739.13`；若完全无排班，则比例底薪和考勤工资均为 `¥0.00`。该归零分支已由端到端用例 `A1b` 覆盖。

> **重要区别：** 人社部工资折算中的月计薪天数 21.75 与月制度工作日 20.67，是法定日/小时工资折算参考口径；本 App 当前“比例底薪”采用员工配置的“当月自然日 − 月休天数”作为排班考勤分母。两者用途不同，不能在未确认业务政策的情况下混用。[1]

## 三、“无排班仍有工资”的验收判定

### 3.1 当前是否还会出现“无排班却自动产生比例底薪”

**草稿（DRAFT）和调整中（ADJUSTING）月份不会。** 自动同步必须先等待排班与员工数据加载完成；加载完成后，即使某员工当月 `empShifts = []`，仍会重算并写入考勤和薪资单，而不是跳过该员工。真实计算器在 `attendanceDays = 0` 时强制将比例底薪置为 0。已冻结（FROZEN）月份则禁止任何自动写入，历史结算只能经差额调整流程处理。此路径专门用于清除未冻结月份中历史残留的考勤工资、加班费、节假日补偿。

| 场景 | 考勤工资 `attendanceSalary` | 是否属于 Bug | QA 预期 |
|---|---:|---|---|
| 草稿月（DRAFT），员工无任何排班，且无特殊状态 | ¥0.00 | 否 | 通过；比例底薪、加班费、节假日补偿均为 0 |
| 调整中月（ADJUSTING），删除最后一条排班后等待约 0.5 秒 | ¥0.00 | 否 | 通过；自动同步写回 0 |
| 冻结月（FROZEN），修改其它同步依赖 | 保留已确认快照 | 否 | 通过；自动同步必须跳过该月 |
| 应出勤天数异常为 0，例如月休天数 ≥ 当月天数 | ¥0.00 | 否 | 通过；不得回退为全额底薪 |
| 已确认发薪月被冻结后，后来查看时已存在工资 | 保留已确认快照 | 否 | 通过；冻结月禁止自动重算 |
| 无排班但总应发仍非 0 | 取决于额外字段 | 需核对来源 | 见下表 |

“无排班但**总应发/实发**非 0”不一定是比例底薪错误。当前薪资草稿会保留或计算下列非考勤字段；QA 必须在薪资卡和绩效补贴页核对来源，而不是仅凭总额判定异常。

| 可能仍非 0 的字段 | 为什么可能存在 | QA 判定方式 |
|---|---|---|
| 固定交通/其他补贴 | 规则可能按月固定发放，不按出勤天数归零 | 核对补贴规则 `unit`；`per_day` 必须为 0，固定规则按门店政策处理 |
| 工作绩效、业绩绩效 | 用户在绩效补贴页保存的手工选择或营收结果会被保留 | 核对 `workKPIBonus`、`revenueKPIBonus` 及业务审批依据 |
| 业绩提点 | 独立的 `salesCommission` 控制字段 | 核对营业额/提点审批记录 |
| 奖惩 | 手工奖惩条目 | 核对奖惩明细与审批 |
| 调休兑现 | 已将历史调休兑换为现金 | 核对 `compOffCashOut` 和兑换记录 |
| 已确认发薪历史 | 冻结月份的正式结算数据 | 不应被排班清空动作篡改；需在差额调整流程处理 |

因此，QA 的通过标准不应写成“无排班时总金额必须为 0”，而应写成：**无排班时考勤底薪、加班费、节假日现金补偿必须归零；任何剩余金额必须可追溯至规则化补贴、明确人工控制字段或已冻结的历史结算。**

## 五、H5 / iOS 手工回归用例

所有用例先在 H5 执行，再在 iPhone SE 级别和 Pro Max 级别设备各执行一次。每个用例需截图保存“操作前、操作后、薪资总览”三个状态；涉及冻结的用例还需截图月报状态。

### Case M01：空排班归零

| 项目 | 操作 | 预期结果 |
|---|---|---|
| 前置 | F01 在测试月已有至少 1 条正常排班，薪资卡显示非 0 考勤工资 | 可观察归零前状态 |
| 操作 | 删除 F01 当月最后一条排班；保持月度状态为 DRAFT 或 ADJUSTING；等待至少 1 秒 | 自动同步完成 |
| 考勤验证 | 打开薪资总览 | 出勤天数 0、总工时 0、加班费 0、节假日补偿 0、考勤工资 0 |
| 薪资验证 | 检查薪资卡和薪资统计 | 比例底薪不得残留；如总额非 0，逐项核对第四节列出的合法来源 |
| 失败判定 | 考勤工资仍为正数，或没有等待数据加载完成就保留了旧考勤记录 | 阻断发布 |

### Case M02：比例底薪复算

对 F01 填写 22 个不同日期的 8 小时班次，不填节假日、加班、补贴或绩效。预期出勤天数为 22、应出勤天数为 23，考勤工资应为 **¥5,739.13**。再补第 23 天班次，考勤工资应回到 **¥6,000.00**。删除全部班次后，考勤工资必须回到 **¥0.00**。

### Case M03：节假日普通班次与倍率

为 F01 配置 7 月 1 日为倍率 3 的节假日，并在该日录入普通 8 小时班次。进入“生成薪资单”，应出现节假日处理项；选择“拿钱”后，节假日补偿为日薪的额外 2 倍。改选“换休”并重新触发自动同步，现金节假日补偿必须被剔除，同时调休余额应生成一条 `source=holiday` 的记录。配置倍率为 1 或删除该日班次时不得产生补偿或决策项。

### Case M04：节假日决策入口与历史选择保持

点击排班控制栏的钞票图标“生成薪资单”。若存在实际节假日工作记录，必须打开“节假日上班处理”弹窗；若没有记录，则可直接生成。对同一记录选择“换休”后，切换页面、返回、修改无关排班并等待自动同步，选择仍须保持为“换休”，不得被重置为“拿钱”。

### Case M05：调休余额单一来源与幂等

创建一条节假日换休和一条加班换休余额。薪资总览、员工薪资卡、班次编辑弹窗的余额应一致；节假日余额与加班余额应按来源分开展示。对同一调休排班连续点击生成薪资单两次，余额只能扣减一次。手动减少 0.5 天时，若现有余额为 1 天，应剩余 0.5 天；尝试减少大于可用余额的天数时，必须提示“余额不足”且不得修改任何记录。

### Case M06：跨月格子锁定防线

冻结 6 月，在 7 月日历中找到显示的 6 月相邻日期。依次尝试：点击编辑、清空、批量选中删除、班次快速填充、工时快速填充。每次都必须提示存在已锁定月份，且 6 月排班数据不变。随后将 6 月进入 ADJUSTING，再执行相同操作，应允许写入。

### Case M07：快照恢复的部门隔离

在同一月份分别建立前厅和后厨排班，并给前厅保存快照。修改两部门排班后恢复前厅快照。预期：前厅恢复为快照内容；后厨排班完全不变。若该月已冻结，恢复操作必须被拒绝。

### Case M08：月份和员工隔离

为 F01 在 6 月、7 月分别建立不同排班；同时为 F02 在 7 月建立排班。打开 F01 的 7 月薪资，必须只统计 F01 的 7 月排班。为 F01 同一天录入两个班次时，总工时应累加，但出勤天数只计 1 天。

### Case M09：兼职规则

为 P01 在节假日配置日期录入 8 小时班次。兼职小时模式的考勤工资应为 `工时 × 小时工资`，不应增加全职节假日倍率补偿。此用例用于避免全职薪酬规则串入兼职计算分支。

### Case M10：冻结月和已确认工资

先完成某月发薪确认，使其状态为 FROZEN；然后删除或修改该月排班。应用必须阻止直接修改，自动同步也不得重算并清除历史工资。将月份切换到 ADJUSTING 后，才允许编辑，并需按差额调整流程复核最终金额。

## 六、异常处置与运维排查

遇到“无排班但金额不为 0”时，按以下顺序排查。不要先删除薪资单或覆盖数据，以免丢失诊断证据。

| 顺序 | 检查内容 | 期望/处置 |
|---:|---|---|
| 1 | 月度状态 | FROZEN：属于锁定历史，不自动重算；DRAFT/ADJUSTING：继续排查 |
| 2 | 是否加载完成并等待至少 1 秒 | 未加载完成时不要作结论；自动同步有 500ms 防抖 |
| 3 | 考勤字段 | `attendanceDays=0` 时 `attendanceSalary`、加班费、节假日补偿必须为 0 |
| 4 | 排班数据 | 核对该员工、该 `YYYY-MM` 是否还有普通班次、特殊状态或跨月误写单元格 |
| 5 | 薪资分项 | 逐项检查固定补贴、绩效、业绩提点、奖惩、调休兑现、预支扣款 |
| 6 | 规则配置 | 检查固定补贴是否本应按月支付；如业务政策不允许无出勤支付，应关闭该规则或设为按天 |
| 7 | 异常留证 | 截图、导出薪资明细、记录员工 ID/月/排班条数/锁定状态，提交缺陷单 |

运维在升级前应备份本地薪资和排班数据。若发现旧节假日调休余额，应用会在启动后把它迁移到统一调休余额源；迁移完成后，业务页面只读取统一来源，避免历史双数据源重复展示或重复消费。
