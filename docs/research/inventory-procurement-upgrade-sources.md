# 库存与采购升级方案：研究要点

## Apple 人机界面指南：字体与动态字号

来源：https://developer.apple.com/design/human-interface-guidelines/typography

- Dynamic Type 是 iOS 与 iPadOS 的系统级文字可读性设置；应用需要在所有字号下保持可读与可用。
- Apple 要求布局适配全部字体大小，同时有意义的图标随字体放大。
- 大字号下应尽量减少截断；受限横向空间中的内联信息会拥挤时，应改用垂直或减少列数的布局，而不是缩小文字到不可读。
- 无论字号如何变化，信息层级应保持一致。

## Shopify：采购订单流程

来源：https://www.shopify.com/blog/purchase-orders

- 采购订单应连接供应商、商品、数量、约定价格、预期到货与付款条件，并与库存、财务信息保持可追溯关联。
- 收货入库与付款是不同阶段；采购订单、收货记录和发票应进行核对，异常应交由人工处理。
- 支付完成后才关闭结算，同时保留支付与供应商绩效记录。

## 对本项目的适用结论

- 三端排版应由语义字号、平台和可用宽度共同决定，不能沿用单一固定字号；紧凑表格应在空间不足时调整列结构、显示方式或进入明细，而非无底线缩字。
- 采购业务需要将“商品主档/供应商渠道名称”“采购或收货流水”“付款与备用金分摊”拆成可独立审计、可人工纠错的事实，禁止一个字段同时承担三种业务含义。
- 商品合并必须保留原始采购流水、供应商名称别名和完整审计记录，并支持反向拆分。

## Oracle：采购支出分析与付款表现

来源：https://www.oracle.com/fusion-data-intelligence/erp-analytics/spend-product-tour/

Oracle将采购支出、员工费用与付款表现置于同一套财务和采购 KPI 视图中，并支持按分类、业务单元、地区、时间等维度切分。该页面示例明确提出“供应商支出 Top 10”“支出分类随时间变化”“活跃供应商贡献”等问题，并支持从汇总卡片下钻到逾期付款与发票明细。

## 对本项目的适用结论（补充）

- 比较不应是孤立的“上月同比”按钮，而应是一个统一的比较上下文：主期间、基准期间或预算、筛选范围（分类/集团/供应商/酒款）、计量口径（金额/数量/均价/占比/价格变化/未付款）和下钻对象。
- 总览卡、采购占比、集团占比、供应商占比与分类汇总应读取同一比较上下文；用户点击任一卡片后应携带相同筛选条件进入既有当月进货页，而不是生成另一套报表页面。
- 供应商付款表现应来自采购应付款事实与备用金支付事实的关联，展示待付、部分付、已付、逾期/临期、付款周期和未匹配项目，不能以单一“自采”布尔字段推断。

## 当前代码基线审阅

当前烈酒模型已经具备以下基础：`SpiritItem` 有标准中文名、可选英文名、分类、集团、主供应商、供应商别名、关联酒库档案 ID 与关联置信度；采购流水保留 `rawName`、`itemId`、供应商、集团与分类快照；月度台账已经区分期初量、进货量、消耗量与期末量，并提供 `setActualClosing` 的月末盘点能力。品牌集团的中文/英文主名已经关联保存，但关键词仍拆为 `keywordsZh` 和 `keywordsEn` 两个独立数组。供应商仅有 `isSelfBuy` 布尔标记，尚不足以描述网络采购、付款方式、账期、订单、收货与多笔支付。

工作台已有酒库智能匹配和手动查询候选的基础实现，也会保存供应商采购别名；但库存、当月进货与酒库详情尚未使用统一的“连接管理”入口，且现有关键词、排序、快速分类、付款以及比较分析并非同一事实模型。快速选择分类目前位于采购详情区域，默认横向滚动，未满足需要在本期消耗卡下默认展开且可折叠的要求。
