# 补贴、工作绩效与业绩绩效：全链路参考

**适用版本：** `main` 分支，唯一结算模型。本文说明三个金额在当前系统中的唯一含义、计算、保存、展示、同步和风险边界。

## 1. 总体关系

三个金额不是彼此覆盖的关系，而是同一薪资单上的三个**独立分项**。它们都以员工和月份为边界：`employeeId + month` 唯一定位一份薪资单。员工档案保存规则，薪资单只保存用户操作的控制字段及系统结算后的分项金额。

```text
员工档案规则 + 月份 + 实际出勤天数 + 薪资单控制字段
                         ↓
              settlePayrollExtras(...)
                         ↓
补贴合计 + 工作绩效 + 业绩绩效 + 奖惩小计
                         ↓
综合额外 → 应发薪资 → 扣除预支/社保/个税 → 实发薪资
```

> 金额计算的唯一入口是 `lib/labor/payroll-extras.ts` 中的 `settlePayrollExtras()`。薪资草稿、绩效编辑预览、绩效只读页、薪资统计卡、考勤详情、导出和月度归档均应使用同一口径，页面不得自行重新计算。

## 2. 三类金额的固定定义

| 名称 | 含义 | 配置来源 | 控制字段 | 结算结果字段 |
|---|---|---|---|---|
| **补贴合计** | 所有符合当月发放条件的补贴总和。 | `Employee.allowanceRules` | `allowanceOverrides`、固定补贴的 `allowanceDetails` 人工覆盖 | `mealAllowance`、`transportAllowance`、`otherAllowance` |
| **工作绩效** | 工作KPI规则中，用户为每条规则选中的档位金额之和。可为正、零或负。 | `Employee.workKPIRules` | `workKPISelections` | `workKPIBonus` |
| **业绩绩效** | 按营业数据、门槛、发放模式和计算方式计算出的唯一业绩奖励。 | `Employee.revenueKPIRules` | `revenueActuals` | `revenueKPIBonus` |

### 2.1 补贴合计

补贴规则包含 `id`、名称、金额、类型、单位、启用状态、周期模式和生效月份。其基础公式为：

```text
补贴合计 = 餐补 + 交通补贴 + 其他补贴
```

其中各分项分类规则如下。

| 补贴类型/单位 | 进入的分项 | 计算方式 | 零出勤处理 |
|---|---|---|---|
| `meal_per_day` 或 `per_day` | 餐补 | 规则单价 × 实际出勤天数 | **强制为 ¥0**。旧薪资单中残留金额不能继承。 |
| `transport_fixed` | 交通补贴 | 固定金额，按月/季/年发放条件判断 | 按规则发放，不因零出勤自动变更。 |
| `custom_fixed` 等其他固定规则 | 其他补贴 | 固定金额，按月/季/年发放条件判断 | 按规则发放，不因零出勤自动变更。 |

季度和年度补贴会先判断本月是否为发放月。自然季度只在3、6、9、12月发放；滚动周期从规则生效月开始计算。固定补贴可保存明确人工覆盖金额；按天补贴不允许人工金额残留。

### 2.2 工作绩效

工作绩效不取决于出勤天数、营业额或旧工资金额。每一条已启用的工作KPI规则有多个档位，员工本月选择哪个档位，就只取该档位金额：

```text
工作绩效 = Σ 每条已启用工作KPI的已选档位金额
```

未选择档位视为 ¥0。负向档位是合法的工作绩效扣减，但只影响工作绩效，不会影响业绩绩效或补贴。

### 2.3 业绩绩效

**业绩绩效是唯一业绩奖励概念。**过去的“业绩提点”不再是独立金额、独立展示或独立公式；如果规则采用比例方式，也只是业绩绩效的一种计算方式。

每条业绩规则有数据源、档位门槛、发放模式和计算方式。

| 配置项 | 可选值 | 作用 |
|---|---|---|
| 数据源 | 总营业额、扣手续费营业收入、净利润、经营大类、手动填充 | 确定实绩数值的业务来源。 |
| 发放模式 | 取最高档、叠加发放 | 达标后只取最高一档，或将所有已达标档位累加。 |
| 计算方式 | 固定金额、按比例 | 固定金额直接取档位金额；按比例为实绩 × 档位比例。 |
| 封顶金额 | 0或正数 | 正数时限制单条规则最终金额上限。 |

计算公式为：

```text
业绩绩效 = Σ 每条已启用业绩规则的计算结果

取最高档：实绩达到多个门槛时，仅取最高门槛对应金额或比例结果
叠加发放：实绩达到多个门槛时，累加所有已达标金额或比例结果
按比例：单档结果 = 实绩 × 档位比例
```

业绩实绩未填写时按0计算；规则未启用时不参与计算。业绩绩效不因出勤为0自动清零，除非业务规则本身不达标；这是因为它由经营业绩规则决定，而不是按天补贴。

## 3. 关联与总额公式

| 名称 | 公式 | 是否保存为独立金额 |
|---|---|---|
| 补贴合计 | 餐补 + 交通补贴 + 其他补贴 | 展示时汇总；底层保存三个分项。 |
| 绩效补贴 | 补贴合计 + 工作绩效 + 业绩绩效 | 展示概念，不另存第二份合并金额。 |
| 奖惩小计 | 独立人工奖惩项目之和 | 保存为 `rewardPenalty` 及项目明细。 |
| 综合额外 | 补贴合计 + 工作绩效 + 业绩绩效 + 奖惩小计 | 展示概念，不作为另一套结算引擎。 |
| 应发薪资 | 考勤工资 + 补贴合计 + 工作绩效 + 业绩绩效 + 奖惩小计 + 调休兑现 | 保存为 `grossSalary`。 |
| 实发薪资 | 应发薪资 − 个人社保 − 公积金 − 个税 − 已预支 − 备用金人工已付 | 保存为 `finalSalary`。 |

“绩效补贴”和“综合额外”不是可另外编辑的金额；它们是分项的可追溯汇总。因此修改任一规则、档位、实绩、出勤或奖惩后，系统必须重新结算，不能对汇总金额直接累加。

## 4. 保存与实时同步链路

### 4.1 在绩效补贴编辑页保存

编辑页保存的不是合并金额，而是四类可追溯控制信息：

| 控制字段 | 写入内容 | 控制哪个分项 |
|---|---|---|
| `allowanceOverrides` | 某补贴是否启用 | 补贴合计 |
| `allowanceDetails` | 固定补贴的明确人工覆盖及审计依据 | 补贴合计 |
| `workKPISelections` | 每条工作KPI对应的已选档位ID | 工作绩效 |
| `revenueActuals` | 每条业绩规则的实绩数字 | 业绩绩效 |

保存顺序为：先写控制字段，再调用 `buildPaySlipDraft()`，由草稿构建函数读取刚保存的控制字段并调用 `settlePayrollExtras()`，最后原子写回新的完整薪资单。这样在同一个页面生命周期内返回薪资卡，也会以 `paySlips` 最新状态重新渲染，而不依赖退出或重启。

### 4.2 排班、考勤和自动同步

排班变化只会先改变实际出勤天数和考勤工资。自动同步随后再次构建草稿，并从现有薪资单保留 `allowanceOverrides`、`allowanceDetails`、`workKPISelections` 与 `revenueActuals`。因此：

- 出勤从1天变为0天时，按天餐补会从单价×1变为¥0；
- 工作绩效与业绩绩效控制字段不丢失，金额会按同一规则重算；
- 固定补贴只遵从规则和明确人工覆盖，不被零出勤误清零；
- 跨月或跨员工不会混用控制字段，因为薪资单按 `employeeId + month` 定位。

### 4.3 跨设备同步

完整薪资单持久化在 `labor_payslips_v1`，该键已在云同步引擎、权限模型与备份模型中注册。云同步传输的是包含控制字段和分项结算结果的薪资单；接收端加载后使用最新记录渲染。控制字段是再结算依据，分项金额是本次结算结果和审计显示依据。

## 5. 展示与导出位置

| 位置 | 展示内容 | 是否重新计算 |
|---|---|---|
| 绩效补贴编辑页 | 绩效补贴、补贴、工作绩效、业绩绩效四格及规则明细 | 用唯一结算函数做实时预览。 |
| 绩效补贴只读页 | 同一四格和明细 | 用唯一结算函数读取当前薪资单控制字段。 |
| 薪资统计卡 | 补贴合计、工作绩效、业绩绩效、奖惩小计、综合额外、应发/实发 | 读取薪资单分项并按固定公式汇总。 |
| 考勤薪资详情 | 餐补、交通补贴、其他补贴、工作绩效、业绩绩效、综合额外 | 读取薪资单分项并按同一公式汇总。 |
| Excel导出 | 补贴合计、工作绩效、业绩绩效、奖惩小计、应发/实发 | 读取薪资单分项，不存在业绩第二列。 |
| 月度归档/差额调整 | 三类补贴分项、工作绩效、业绩绩效和奖惩分项 | 冻结为快照；冻结后改动通过差额调整而非静默覆盖。 |

## 6. 已删除名称、剩余字符与风险结论

以下名称和字段已不再属于运行时业务模型：

| 旧名称/字段 | 当前状态 | 处理方式 |
|---|---|---|
| `performanceBonus` / “绩效奖金” | 已废弃 | 不计算、不展示、不导出；加载旧本地薪资单时物理删除。 |
| `salesCommission` / “业绩提点” | 已废弃并合并为业绩绩效 | 不计算、不展示、不导出；加载旧本地薪资单时物理删除。 |
| “业绩”作为独立薪资简称 | 禁止使用 | 所有薪资相关页面统一显示“业绩绩效”。 |

当前生产代码中保留 `performanceBonus` 与 `salesCommission` 两个英文字符的唯一位置，是加载旧本地薪资单时的**删除键列表**。它们不会被读取成金额、不会映射为新字段、不会参与同步计算；其作用是防止历史数据回流。

`types.ts` 中“业绩绩效奖金”的注释只是中文描述，指向现有 `calcRevenueKPIBonus()`，不是旧字段或第二个金额概念。

## 7. 核对清单

每次核对一名员工时，应按以下顺序检查：

1. 当前月份、员工ID和薪资单是否匹配。
2. 实际出勤天数是否正确；按天补贴是否等于单价×出勤天数。
3. 每条补贴是否启用、是否到达月/季/年发放期、是否存在固定补贴的明确人工覆盖。
4. 每条工作KPI是否有已选档位，档位金额是否正确。
5. 每条业绩规则的实绩、门槛、最高档/叠加、固定/比例和封顶是否正确。
6. 补贴合计、工作绩效、业绩绩效、奖惩小计与综合额外是否满足上述公式。
7. 应发和实发是否仅在允许的扣除项目上出现差异。
8. DRAFT月份允许实时重算；FROZEN月份必须走差额调整。
