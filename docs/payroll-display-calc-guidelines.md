# 薪资卡片与关联逻辑重构分析及开发规范报告

**导出时间**：2026年08月06日
**针对问题**：特殊扣薪双重计算、存入调休未联动加班费、业绩绩效字段语义不清

## 1. 影响范围及重构清单

本次深度扫描发现，薪资卡片的三个核心问题并非仅存在于用户界面层，其底层计算逻辑和数据依赖已经渗透到了多个核心引擎中。为了彻底解决这些问题，我们对相关模块进行了全面的重构和清理。

在导出引擎（`lib/labor/export.ts`）中，Excel 和 PDF 导出直接读取考勤引擎持久化的 `dailyRate` 与 `proportionalBaseSalary`。比例底薪统一为“日薪原始基数 × 实际出勤天数”，只有缺少该字段的历史考勤才按其已结算金额兼容读取，避免新数据由导出层重新计算或反推。在 Excel 导出的总表和明细表中，「比例底薪」和「特殊扣薪」保持独立列；绩效相关列固定为「补贴合计」「工作绩效」「业绩绩效」和「奖惩小计」，并与App实时结算结果完全一致。

考勤卡片详情模块（`app/labor-attendance.tsx`）也受到了影响。原本的 `saveRewards` 函数在保存奖惩数据时，其内部调用的 `buildPaySlipDraft` 因为缺少最新的调休记录等依赖，会错误地覆盖其他模块的计算结果。重构后，我们补充了对 `compOffEntries` 和 `holidayCompOffEntries` 的完整依赖，并统一了内部展示的「考勤工资」和「比例底薪」的计算口径。

在状态引擎方面，真实生产计算器 `attendance-calculator.ts` 先计算日薪原始基数“月底薪 ÷ 当月应出勤天数”，再计算并持久化比例底薪“日薪 × 实际出勤天数”。展示和导出读取这一明确字段，而不是从 `attendanceSalary` 反推。统一闭环为：比例底薪加上加班费和节假日薪资，再减去特殊扣薪，等于最终的考勤工资。

此外，专项测试直接调用生产日薪和比例底薪函数，覆盖日薪原始精度、比例底薪累计、全勤闭环、零出勤、历史数据兼容、自动同步依赖完整性以及绩效补贴唯一结算口径。

## 2. 问题产生根因分析

| 问题表现 | 根本原因 | 架构层面的本质 |
| :--- | :--- | :--- |
| **特殊扣薪双重计算** | 底层引擎计算 `attendanceSalary` 时已减去 `totalSpecialDeduction`。但前端在推算 `baseSalary` 时使用了简单的减法，得到了“比例底薪减去特殊扣薪”的结果。随后界面又单独渲染了一个“特殊扣薪”区块，导致视觉和心算上特殊扣薪被扣除了两次。 | 底层存储的聚合字段与前端拆解展示的精细化需求不匹配。 |
| **存入调休未联动加班费** | 负责监听状态变化并重算薪资的 `autoSync` 机制，其 `useEffect` 依赖数组中遗漏了调休记录表（`compOffEntries`）。当用户存入调休时，排班表并未改变，因此不会触发薪资重算。 | 跨模块的状态联动缺乏统一的事件总线，强依赖 React 渲染周期的钩子函数，极易漏写依赖。 |
| **业绩绩效字段语义错位** | 历史遗留的重复业绩字段被不同页面按不同含义读取，导致同一金额在绩效页和薪资卡不一致。 | 缺乏全系统统一的字段级数据字典和唯一结算入口。 |

## 3. 开发规范与防错建议

为了避免类似问题在未来的考勤和薪资模块中再次发生，建议团队在后续开发中严格遵循以下规范。

**UI 与导出必须读取专用持久化字段或统一读取函数**。比例底薪由生产考勤计算器持久化为 `proportionalBaseSalary`；界面和导出通过 `getAttendanceBaseSalary` 读取。旧历史数据缺少该字段时才允许兼容反推，任何新数据和 UI 组件都禁止从聚合的 `attendanceSalary` 自行推算。所有拆分展示都必须满足数学闭环，并有生产函数级单元测试。

**自动同步机制的依赖必须通过工具进行静态分析**。React 钩子函数的依赖缺失是导致状态不同步的最常见原因。在本项目这种高度复杂的联动引擎中，漏掉一个依赖就会导致整个模块的数据失效。建议强制启用 `eslint-plugin-react-hooks` 的 `exhaustive-deps` 规则并将其设置为错误级别。长远来看，应将自动同步逻辑从 React 组件中剥离，移入状态管理库的订阅监听器中，实现真正的状态驱动。

**字段名称必须与其业务语义严格一致**。如果在迭代中发现某个字段的名称与实际业务含义不符，必须重命名底层字段或修改界面的标签文本，绝不能通过前端的强行解释来掩盖。在类型定义文件中，必须维护严格的注释文档，所有跨组件使用的核心金额字段，都必须在注释中清晰写明其计算来源和业务含义。

**任何用户界面的修改必须同步至导出引擎**。薪资和考勤模块具有强烈的“所见即所得”要求。App 界面上看到的数字和明细，导出的 Excel 和 PDF 报表必须保持完全一致。建议将界面展示的列和 Excel 导出的列抽象为共享的配置架构，确保在增删改列时，界面和报表能够同时且一致地生效。
