# 员工档案统一排序重构技术总结

**项目**：Cocktail R  
**主题**：员工档案自定义排序的全链路统一  
**状态**：已实现、已验证、已推送  
**相关提交**：`d0afa9d`、`3806c75`

## 1. 重构目标

本次重构将员工档案中的部门顺序与员工 `sortOrder` 确立为所有**在职员工可见列表**的唯一排序来源。此前，多个页面分别使用 Store 原数组顺序、局部 `sortOrder`、硬编码部门顺序或未排序筛选结果，导致同一名员工在排班、考勤、薪资、预支和导出中可能出现不同位置。

重构后的统一规则是：先按员工排序页保存的部门顺序 `deptOrder`，再按同一部门内的员工 `sortOrder`，最后以员工代号和 ID 做稳定兜底。该规则不修改 Store 原数组，而是始终返回新的排序数组。

```text
员工档案排序页
  ├─ 部门顺序：deptOrder
  └─ 员工顺序：Employee.sortOrder
           ↓
employee-profile-order.ts
           ↓
排班 / 考勤 / 薪资 / 预支 / 月报 / 导出 / 导入模板 / 新建月结快照
```

## 2. 单一排序工具

核心实现位于 `lib/labor/employee-profile-order.ts`。

| 工具 | 适用范围 | 排序规则 |
|---|---|---|
| `sortEmployeesByProfileOrder` | 跨部门员工列表 | `deptOrder` → `sortOrder` → `code` → `id`。 |
| `sortEmployeesWithinProfileGroup` | 已完成部门分组的列表 | `sortOrder` → `code` → `id`。 |

这两个函数都使用不可变方式返回新数组。页面不得通过 `employees.sort(...)` 修改 Store 数据，也不得依赖 AsyncStorage 或同步载荷中的数组位置。

## 4. 历史数据例外与冻结语义

并非所有“员工相关数据”都应跟随当前档案排序改变。以下两个历史对象必须保留原始历史语义。

| 历史对象 | 当前规则 | 原因 |
|---|---|---|
| 离职员工档案 | `app/labor-archived.tsx` 按 `archivedAt` 倒序 | 离职归档的时间线是历史事实；后续调整在职员工顺序不得篡改归档浏览顺序。 |
| 已冻结月结排班 | `labor_month_close_archives_v1` 中已存在的 `scheduleByDept.*.employeeIds` 不迁移、不重写 | 月结快照是结算时点的证据；后续档案重排只影响新建快照。 |

因此，本次重构的边界为：**在职的实时业务视图跟随员工档案排序；已经归档或冻结的历史视图保留当时的历史顺序。**

## 5. 非排班模块审计

### 5.1 薪资核算与员工支付

薪资核算页、薪资预支、备用金人工匹配、总月报工资明细、独立预支页和导出都已经适配。薪资草稿生成、个税累计、独立补发、预支扣减和调休结算以 `employeeId` 做键值计算，不渲染员工列表，也不依赖员工数组顺序；因此不需要排序改造。

### 5.2 审批流

代码库中不存在独立的“审批流”实体、员工审批 API、审批 SQL 表或审批人员列表。当前业务流程中的“月结确认”“差额调整”“薪资单锁定”是按月份和记录 ID 管理的状态机，而不是人员待办审批队列。若未来新增审批中心，审批人、申请人或抄送人选择器必须直接使用 `sortEmployeesByProfileOrder`。

### 5.3 假期额度与休假

当前系统包含节假日配置、调休余额、加班换休和排班特殊状态，但不存在独立的年假/病假额度账户与员工假期审批列表。调休余额由 `employeeId` 关联的明细条目组成，结算器按可用条目和到期时间处理，并不生成按员工排序的可见集合。未来若建立假期额度总览或请假申请列表，必须按下列规则处理：实时在职列表使用统一排序工具；已审批、已结算或已过期记录按照业务日期保留历史顺序。

### 5.4 后端、Worker 与数据库

当前员工档案没有独立的 Worker API、D1 SQL 查询或服务器端员工表排序逻辑。员工档案通过 `labor_employees_v1` 本地持久化，并作为受控同步模块同步；`sortOrder` 和部门顺序随档案数据一起同步。因此，当前排序统一是在客户端展示、导出和新快照创建层完成的，未发现后端排序缺口。

## 6. 自动化防退化策略

`tests/employee-profile-order-sync.test.ts` 覆盖以下场景：

1. 验证部门顺序、`sortOrder`、代号和 ID 构成稳定的全局排序。
2. 模拟员工在排序页上移后，验证排班网格、考勤概况与预支选择器同步变化。
3. 验证新建月结快照按冻结当时的档案顺序写入 `employeeIds`。
4. 验证离职员工按归档时间排序，不被实时档案顺序重排。
5. 静态检查在职员工可见页面、导入和导出、月结快照均显式调用统一排序工具。

移动端长列表回归脚本为 `scripts/h5-employee-order-mobile-e2e.mjs`，对应命令为：

```bash
pnpm test:h5:employee-order
```

该脚本用 120 名逆序写入的员工验证考勤概况排序、完整渲染、滚动容器、根级宽度和连续帧间隔。详见《移动端前端组件性能卡顿监控规范》。

## 8. 后续开发规范

> 所有实时在职员工列表必须在筛选、分组和渲染前调用统一排序工具；任何历史归档、冻结快照和审计记录必须保留业务发生时的原始历史顺序。

新增人员选择器、审批人选择、请假人员列表、绩效批量设置或导出模块时，必须完成以下检查：

| 检查项 | 要求 |
|---|---|
| 数据源 | 使用员工档案 Store，不能维护第二份列表顺序。 |
| 排序 | 跨部门调用全局工具；已分部门调用组内工具。 |
| 历史数据 | 明确写出使用实时顺序还是冻结/归档顺序。 |
| 测试 | 增加“逆序存储 → 正序显示”的断言。 |
| 移动端 | 若页面是长列表，接入本项目的 H5 长列表性能规范。 |
| 同步 | `employees` 或 `deptOrder` 改变时，相关 `useMemo` / `useEffect` 依赖必须完整。 |

违反上述规则的局部排序、按姓名排序、按创建时间排序或依赖数组原始位置的实现，都应视为排序架构回归。
