# 采购、库存与月报系统重构方案

**状态：待确认后分批实施**  
**范围：烈酒、啤酒、葡萄酒、采购档案、供应商、网络采购、备用金、库存盘点、总月报与分析比较**

> 本方案的核心不是把所有资料堆进一个页面，而是建立清晰的事实边界：**采购渠道归属谁、采购了哪个品类、是否已收货、是否已付款、库存如何核算、总月报如何只读汇总**，每件事都只能有一个权威来源。

## 1. 已确认的业务边界

| 领域 | 权威事实源 | 管理入口 | 总月报职责 | 禁止行为 |
|---|---|---|---|---|
| 烈酒供应商 | 烈酒采购档案 | 烈酒库存 → 采购档案 → 供应商管理 | 只读汇总烈酒采购和付款 | 总月报另建烈酒供应商；按名称猜测合并 |
| 啤酒 / Beer 分类 | **烈酒进销存内的一级分类**，复用烈酒供应商管理 | 烈酒库存与烈酒采购档案内的“啤酒 / Beer”筛选/分类 | 单独汇总啤酒采购、付款与成本行 | 单独页面、单独模块、第三套供应商资料；将啤酒金额混入非啤酒分析 |
| 葡萄酒供应商 | 葡萄酒采购档案 | 葡萄酒库存 → 采购档案 → 供应商管理 | 只读汇总葡萄酒采购和付款 | 与烈酒供应商自动合并；按名称推断同一主体 |
| 网络采购渠道 | 归属于对应品类的采购档案 | 烈酒或葡萄酒采购档案 | 显示备用金关联和待关联状态 | 把网络采购伪装成已付款；把链接写进库存主档 |
| 总月报旧供应商档案 | **退役** | 无 | 只读消费模块付款投影 | 新建、编辑或按名称匹配供应商 |

烈酒和葡萄酒即使存在同名供应商，也仍是**两个独立模块内的供应商资料**。未来如确有跨模块同一公司对比需求，只能新增可选的“主体关联”辅助层，并由用户显式确认；该关联不得改变两个模块各自的供应商 ID、排序、付款或采购事实。

## 2. 啤酒是烈酒进销存内的分类，但保持独立核算

啤酒不再拥有独立页面、独立顶级模块、独立供应商库或独立采购工作台。它是**烈酒进销存内的一级业务分类“啤酒 / Beer”**，与威士忌、金酒、朗姆酒等烈酒分类共同出现在同一库存、同一当月进货、同一采购档案和同一供应商管理页面中。烈酒供应商可以同时提供烈酒和啤酒，网络采购渠道也可购买啤酒并通过备用金付款。

**共享的是页面、供应商、网络采购渠道、付款流程和采购档案；独立的是分类事实、库存余额、消耗、价格历史、采购分析、付款汇总和总月报成本行。**

```text
烈酒进销存（一个页面 / 一套供应商 / 一套采购档案）
├── 分类：威士忌、金酒、朗姆酒、……
├── 分类：啤酒 / Beer
└── 付款事实：集中付款 / 备用金分摊 / 待关联

同页内的分类投影
├── 非啤酒烈酒：库存、消耗、价格、分析、付款与月报行
└── 啤酒 / Beer：库存、消耗、价格、分析、付款与月报行
```

每条采购记录至少保存 `inventoryDomain: "spirits"`、`productClass`（其中可为 `beer`）、`supplierId`、`channelType`、`purchaseId` 与 `categorySnapshot`。台账、消耗、价格历史、付款和月报在后台再以 `productClass` 切分；用户仍按现有烈酒页面的正常分类呈现和筛选使用，不增加“仅啤酒”“排除啤酒”或任何额外模式切换。金额、库存、消耗和成本绝不会重复累计或混算。

## 3. 28 项功能优化的模块划分与优先级

优先级定义：**P0** 为数据正确性、可恢复性和阻断性缺陷；**P1** 为核心工作流完整性；**P2** 为分析体验与增强能力；**P3** 为后续扩展。

| 编号 | 需求归类 | 目标模块 | 优先级 | 实施成果与验收 |
|---:|---|---|---|---|
| 1 | 三端字体与布局 | 共享表格/卡片排版令牌 | P0 | iPhone、iPad 分屏/全屏、macOS 窄宽与系统字号下不出现遮挡、消失、断层或关键字过小；空间不足只重排/收纳。 |
| 2 | 重复/近似商品 | 商品整理中心 | P0 | 严格同名归一化仅提示候选；近似名不自动合并；可预览、合并、撤销与拆分，保留采购原名和渠道别名。 |
| 3 | 库存商品链接 | 商品连接管理 | P1 | 商品无论已关联与否均可查看、智能链接、手动链接、更换、解除和新建酒库档案。 |
| 4 | 库存快速分类 | 库存详情 | P1 | 放在本期消耗卡后，默认展开且可收起；更新库存主档和当前采购快照的原子分类选择。 |
| 5 | 期初/期末库存 | 库存盘点命令 | P0 | 仅库存管理允许编辑；期末库存反推消耗；月结后受控调整，不允许其它入口静默改写。 |

| 12 | 分类筛选排序 | 当月进货列菜单 | P0 | 分类多选、未分类、清除、权威分类顺序、名称/金额/数量排序；临时排序不改变分类管理顺序。 |

| 23 | 手动录入 | 当月进货上浮卡 | P1 | 改用底部上浮卡，保存/取消固定在卡内安全区，保留草稿和键盘避让。 |

| 25 | 关联和归档可见性 | 库存状态投影 | P1 | 明确显示已关联酒库、正在使用、归档、未关联和待处理状态；筛选可组合。 |

## 4. 核心数据模型

### 4.1 采购渠道与采购记录

```ts
interface ProcurementChannelRef {
  module: "spirits" | "wine";
  supplierId: string;
  channelType: "supplier" | "online";
}

interface PurchaseFact {
  id: string;
  /** 啤酒仍属于烈酒进销存域；葡萄酒保持独立域。 */
  inventoryDomain: "spirits" | "wine";
  /** 烈酒域内的分析类：beer 仅作为烈酒内分类，不形成独立页面。 */
  productClass: "spirit" | "beer" | "wine";
  supplierRef: ProcurementChannelRef;
  itemId?: string;
  rawSupplierProductName: string;
  categorySnapshot: string;
  quantity: number;
  unitPrice: number;
  amount: number;
  receivedAt: string;
}

interface PaymentAllocation {
  purchaseId: string;
  source: "direct" | "petty_cash";
  pettyCashRecordId?: string;
  amount: number;
  paidAt: string;
}
```

采购成本来自 `PurchaseFact.amount`，付款状态来自 `PaymentAllocation`。两者不得互相覆盖。网络采购未绑定备用金记录时显示“待关联”；供货商采购可保持“待付”至集中付款。付款分摊总额超过采购金额时应显示“超付”，禁止静默截断。

### 4.2 名称、酒款和渠道别名

标准酒款只保存一个统一中英文名称。供应商的导入名称、票据名称和历史变更名称保存为渠道别名，并带有来源与时间。归一化规则只折叠 Unicode 兼容差异、全半角、连续空格、标点和大小写等**不会改变语义**的差异；近似名、年份、容量、版本或套装差异只能作为候选，必须人工确认。

## 5. 总月报的退役与只读投影

总月报现有独立供应商档案、供应商管理入口和按名称推导货款的逻辑均应退役。迁移不删除历史付款记录，而是增加来源标记：`sourceModule`、`sourceSupplierId`、`legacyPayeeId` 与 `mappingStatus`。

| 历史记录情况 | 迁移结果 | 用户可见状态 |
|---|---|---|
| 已可由明确模块 ID 关联 | 建立模块供应商引用 | 正常显示来源品类和渠道 |
| 旧月报仅有名称、无可靠 ID | 保留旧付款记录，不自动认领 | “历史待归属”，可人工选择来源模块与供应商 |
| 烈酒和葡萄酒同名 | 保持两个独立候选 | 不自动合并；分别可关联到各自模块 |
| 人工手工货款 | 保留为手工历史项 | 可后续归属，不影响采购成本 |

总月报卡片只读取模块付款投影；不能在总月报新建供应商，不能用字符串 `includes` 或同名规则将采购、付款和供应商强行相连。

## 6. 葡萄酒库存需要同步更新的详细清单

葡萄酒不与烈酒共享供应商主档，但应同步采用以下安全能力。

| 模块 | 葡萄酒调整项 | 与烈酒相同部分 | 葡萄酒专属保护 |
|---|---|---|---|
| 三端布局 | 表格字号、行高、列轨道和操作区响应式化 | 同一布局完整性契约 | 长酒名、年份、产区、容量不被截断或误折叠 |
| 供应商管理 | 排序、联系人、付款周期、公司资料、渠道类型、网络采购链接 | 同一资料编辑与排序机制 | 使用葡萄酒模块内独立供应商 ID |
| 当月进货 | 分类/供应商/商品筛选排序，手动录入上浮卡 | 同一表头与列菜单行为 | 保留酒庄、产区、年份、箱规、容量列 |
| 商品链接 | 查看、智能链接、手动链接、更换/解除链接 | 同一纠错入口 | 候选排序加入年份、产区、酒庄、规格权重 |
| 重复整理 | 严格归一化候选、预览合并、撤销与拆分 | 同一可逆流程 | 年份、容量、产区、酒庄不同不得自动合并 |
| 分类快速选择 | 默认展开、可收起、原子更新采购快照 | 同一交互和顺序事实 | 分类可保留红/白/起泡/甜酒等业务体系 |
| 期初期末 | 仅库存管理编辑，受月结保护 | 同一盘点命令原则 | 箱/瓶换算必须保留换算单位和精度 |
| 付款 | 供货商集中付款；网络采购备用金分摊 | 同一金额守恒与待关联规则 | 付款只引用葡萄酒采购行，绝不引用烈酒采购行 |
| 价格卡 | 渠道报价、成本基准、采购价格历史、待确定队列 | 同一待处理入口 | 支持年份变化导致的价格比较隔离 |
| 分析 | 渠道、酒庄、产区、分类、年份、价格变化和付款状态对比 | 同一比较上下文 | 不与烈酒/啤酒默认合并，只可在总月报跨模块查看 |
| 总月报 | 单独“葡萄酒付款汇总”和品类成本行 | 同一只读卡片/深链模式 | 仍显示独立模块来源与葡萄酒供应商 |

## 7. 实施顺序

| 阶段 | 内容 | 优先级 | 完成条件 |
|---|---|---:|---|
| A | 三端排版、表格安全区、统一排序、分类筛选、成对集团关键词 | P0/P1 | 宽度与字体倍率回归通过；排序无第二来源 |
| B | 商品连接、重复候选、期初期末盘点、快速分类 | P0/P1 | 无自动误合并；月结保护、可重试和撤销通过 |
| C | 烈酒采购档案扩展；啤酒纳入烈酒页面内分类 | P0 | 无独立啤酒页面或模块；啤酒共享渠道但在同页内独立库存/分析/月报行；付款不混算 |

| F | 总月报旧供应商退役和只读付款投影 | P0/P1 | 无名称匹配，无供应商编辑入口，历史记录可追溯 |
| G | 比较分析、价格待处理、累计采购、附件元数据 | P2 | 仅基于真实事实计算，支持下钻和筛选保留 |

## 8. 测试、迁移和验收

每个阶段必须运行 `pnpm check`、`pnpm test`、`git diff --check`，通过后提交并以 `env -u GH_TOKEN git push` 推送。除单元测试外，必须补齐以下验收：

1. iPhone、iPad 分屏/浮窗、macOS 窗口缩放及系统字体倍率下的视觉回归；关键操作不可遮挡、不可消失。
2. 同名但不同酒款、相同酒款多渠道别名、错误链接、更换链接、合并预览、撤销和拆分的领域测试。
3. 网络采购一笔备用金拆成多酒款、同采购多次付款、超付、无凭证待关联、断网恢复和并发修改测试。
4. 同一烈酒供应商的啤酒与非啤酒采购：在同一烈酒页面、同一采购档案和同一供应商资料中正确显示；按“啤酒 / Beer”分类筛选、库存、价格历史、付款汇总、分析与总月报行独立，且绝不创建或跳转至单独啤酒页面。
5. 烈酒与葡萄酒同名供应商：两者绝不自动合并；总月报来源标识正确；旧总月报付款无法确定归属时保留待归属。
6. 总月报退役测试：不存在新建/编辑旧供应商入口、无字符串名称匹配、付款卡深链回现有当月进货并保持月份/渠道/状态/分类筛选。
