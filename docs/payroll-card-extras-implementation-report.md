# 薪资卡唯一额外项结算重构报告

## 修复目标

本次修复统一了“绩效补贴详情页”“DRAFT薪资卡”“排班自动同步”三条数据链，确保 **补贴合计、工作绩效、业绩绩效、奖惩小计、综合额外** 均使用唯一结算口径。它直接修复了瑞雪的工作绩效未同步、张忠洋零出勤饭补残留以及综合额外换行为两行的问题。

## 两位员工的精确核对

| 员工 | 旧卡片 | 正确实时结算 | 修复后的卡片 |
|---|---:|---:|---:|
| 瑞雪 | 补贴 ¥2500、工作绩效 `—`、综合额外 ¥2500 | 补贴 ¥2500 + 工作绩效 ¥1700 + 业绩绩效 ¥0 + 奖惩 ¥0 = **¥4200** | 显示五项：¥2500、¥1700、—、—、**¥4200** |
| 张忠洋 | 零出勤但综合额外 +¥15 | 饭补 ¥15/天 × 0天 = **¥0** | 补贴合计、综合额外均为 ¥0 |

## 根本原因

根因并非同一笔钱被重复计算，而是 **读模型滞后于写模型**。

第一，绩效补贴页调用 `settlePayrollExtras()`，直接根据 `workKPISelections` 和当前出勤得到最新金额。薪资卡却直接读取先前保存的 `PaySlip.workKPIBonus`、`mealAllowance` 等聚合字段。保存控制字段后，旧薪资单没有在所有入口立刻完整重建，于是瑞雪详情页为 ¥1700、卡片仍为 0；张忠洋详情页按0天为0、卡片仍保留旧的 ¥15。

第二，排班自动同步和薪资卡对账过去各自保有年度累计个税计算路径。即使金额最终相近，独立公式会让后续变更再次产生分叉。

第三，薪资卡使用 `flexWrap: "wrap"` 且每项固定 `33.333%` 宽度，五项必然排为“3 + 2”两行。这是布局错误，不是金额重复。

## 新的运行规则

| 月份状态 | 卡片数据源 | 是否自动写回 |
|---|---|---|
| `DRAFT` | `settlePayrollExtras()` 基于当前出勤与控制字段实时解析 | 若业务金额变动，以幂等方式重建薪资单 |
| `FROZEN` | 已冻结的薪资单快照 | 否 |
| `ADJUSTING` | 历史快照与显式差额 | 否；只允许差额会话处理 |

金额比较仅覆盖结算引擎拥有的数值字段，故意忽略 `allowanceDetails.calculatedAt` 等展示时间戳，避免渲染后无限写回。

## 防止再次不同步的架构规范

1. **控制字段与聚合字段分离。** 控制字段是补贴覆盖、KPI选择、实绩和出勤；聚合字段只是DRAFT可再生快照，不能成为页面唯一事实来源。
2. **唯一公式入口。** UI、同步、导出和重算都调用 `settlePayrollExtras()` / `buildPaySlipDraft()`；禁止新写 `allowance + KPI` 公式。
3. **读模型状态感知。** DRAFT实时解析，FROZEN只读快照，ADJUSTING只走差额。禁止以“方便展示”为由跨越月份状态机。
4. **写回必须幂等。** 先比较业务金额字段，只有差异才持久化；禁止因时间戳或组件渲染触发持续写入。
5. **跨路径共享辅助。** 年度累计税、预支筛选、金额差异判断必须位于 `lib/labor/` 纯函数模块；页面只编排，不复写业务公式。
6. **双向回归样本。** 每个新增薪资修复必须至少包含“非零规则同步”和“零出勤残留清零”两名独立员工场景。

## 验证矩阵

完整回归覆盖以下项目：瑞雪工作绩效 ¥1700、张忠洋零天饭补 ¥0、冻结快照不重算、卡片五项不换行、原有薪资端到端、路由返回同步、TypeScript、跨组故障注入及两套H5多尺寸端到端测试。

## 本月强制重算方案

“重新计算本月”仅允许 DRAFT 月，并在执行前创建可恢复快照；它保留控制字段、预支、调休与节假日分配，仅清理可再生的当月聚合金额后调用唯一引擎重建。它绝不删除或修改其他月份；跨月异常必须单独列为清单、逐月确认并留审计记录。详细交互与事务流程见 `current-month-safe-payroll-recalculation-plan.md`。
